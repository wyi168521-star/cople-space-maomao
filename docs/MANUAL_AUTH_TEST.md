# 邮箱认证与双人配对：手工验收

这份流程验收真实 Supabase 认证、会话恢复、路由保护，以及 `create_couple` / `join_couple` 两个配对 RPC。页面不使用演示账户代替真实登录。

## 本地准备

- 使用已启动且已应用仓库迁移的本地 Supabase；无需清空或重置数据库。
- `.env.local` 中配置本地项目的 `NUXT_PUBLIC_SUPABASE_URL` 和 `NUXT_PUBLIC_SUPABASE_ANON_KEY`，然后在仓库根目录执行 `npm run dev`。
- 前端固定使用 [http://127.0.0.1:3200](http://127.0.0.1:3200)。认证重定向需允许 `http://127.0.0.1:3200/**` 和 `http://localhost:3200/**`；测试过程中保持相同主机名，避免把两份浏览器存储误认为会话丢失。
- 本地邮件查看器：[http://127.0.0.1:54324](http://127.0.0.1:54324)。若项目关闭了邮件确认，注册会直接登录；要验收确认页，请在启用邮件确认的本地配置下测试。
- 建立两个独立浏览器环境 A / B，例如 Chrome 普通窗口与 Edge 普通窗口，或两个独立浏览器用户配置。两个普通标签页、同一无痕会话内的两个窗口通常共享存储，不能作为两个独立用户。
- 分别准备未注册过的测试邮箱 A / B 和至少 6 位的测试密码。使用本地邮件查看器收信，不需要访问真实邮箱。

## A 注册、确认邮箱并创建空间

1. 环境 A 打开 `/`，未登录时应自动到 `/login`。直接访问 `/pairing` 也应返回 `/login`。
2. 切换到“注册”，输入称呼 A、邮箱 A、密码，点击“创建账户”。请求处理中按钮和输入框应禁用，错误应在表单内显示。
3. 邮箱确认开启时，应显示“去邮箱确认一下吧”，并显示正确的邮箱。此时还没有登录会话，直接访问 `/` 或 `/pairing` 不得进入受保护页面。可点“重新发送确认邮件”检查成功提示或服务端限频错误。
4. 在本地邮件查看器中找到邮箱 A 的确认邮件。复制确认链接，**在环境 A 中打开**，以免确认链接把用户登录到另一环境。确认应回到 `http://127.0.0.1:3200`，随后进入 `/pairing`。如确认后没有会话，返回登录页使用邮箱 A 和密码登录。
5. 配对页应显示称呼 A。默认“创建空间”下，输入双方称呼和在一起的日期，点击“创建我们的小家”。
6. 成功后应进入 `/`，显示双方称呼、日期和完整的 `couple_id`（UUID）。复制空间编号并保存给 B 使用。
7. 刷新首页，仍应登录且保留同一 `couple_id`；访问 `/login` 或 `/pairing` 应回到 `/`。尝试复制编号，验证剪贴板内容完整。剪贴板不可用时，编号仍可见且可选中手动复制。

## B 注册并加入 A 的空间

1. 在独立环境 B 打开 `/`，应到 `/login`，不得自动继承 A 的登录状态。
2. 使用称呼 B 和邮箱 B 注册，按同样方式在环境 B 打开邮件确认链接并登录。应进入 `/pairing`。
3. 选择“加入空间”。先输入明显无效的编号，提交后应显示格式错误且不发送配对 RPC。
4. 粘贴 A 的完整 UUID，点击“加入对方的小家”。等待过程中禁止重复提交。
5. 成功后进入 `/`。B 的 `couple_id` 必须与 A 完全一致；刷新 A / B 页面仍分别使用各自账户，且显示同一个空间。

## 退出、错误和路由保护

| 操作 | 预期结果 |
| --- | --- |
| A 点击“退出登录” | A 回到 `/login`；刷新或直接访问 `/`、`/pairing` 都无法进入受保护页面。B 保持自己的会话。 |
| A 再次登录 | 自动恢复已有成员身份，直接进入 `/`，`couple_id` 不变。 |
| 新的已确认但未配对账户访问 `/` | 重定向 `/pairing`。 |
| 错误密码 / 未确认邮箱登录 | 错误显示在登录表单内，仍留在 `/login`；无伪造会话。 |
| 使用格式正确但不存在的 UUID 加入 | RPC 错误显示在配对页内，不进入首页。 |
| 第三个独立测试账户尝试加入已满空间 | RPC 应拒绝，第三个账户仍未配对；A / B 成员关系不变。可使用第三个独立配置，或在 B 明确退出后切换测试账户。 |
| 未配对用户的成员查询断网 / 返回失败 | 显示“暂时无法读取你的小家”和重试按钮，不得把失败当作“没有空间”并继续创建/加入；恢复网络后重新读取。 |
| 已登录状态下刷新页面 | 初始化完成前不闪现未配对表单；最终路由符合服务器中的成员关系。 |
| 关闭前端 Supabase 配置后单独启动测试 | 登录服务不可用，按钮禁用；不能生成演示会话或进入配对页。验收后恢复本地配置。 |

## F12 排查

在发生问题的浏览器环境打开 F12，先看 **Console**，再看 **Network**。开启 Preserve log 有助于保留邮件回跳与路由切换前的请求。只记录状态码和经过脱敏的错误消息；不要复制密码、API 密钥、访问令牌、刷新令牌或完整认证链接。

1. **Console**：检查是否出现组件渲染异常、请求失败、跨域或网络连接错误。页面应能把认证与 RPC 失败显示为可读的行内提示。
2. **注册与确认**：Network 中检查 `/auth/v1/signup`（或确认请求）、`/auth/v1/resend` 的状态及错误消息。确认链接过期或已使用时，重新发送确认邮件。邮件链接中的 token 也属于凭证。
3. **登录 token**：检查 `/auth/v1/token?grant_type=password` 是否成功。确认请求的目标确实是本地 Supabase，而非其他项目。响应是否含会话可在本机检查，但不要分享其中的 token。登录失败时根据响应错误排查邮箱确认、密码或限频。
4. **成员身份读取**：检查 `/rest/v1/profiles`、`/rest/v1/couple_members`、`/rest/v1/couples` 的状态和响应。成功的空成员结果表示尚未配对；失败响应表示读取失败，应看到重试界面。
5. **创建 RPC**：Network 应看到 `POST /rest/v1/rpc/create_couple`，请求参数是 `p_name_a`、`p_name_b`、`p_start_date`。成功响应应返回空间 UUID，随后刷新成员身份并进入首页。不得改为客户端直接插入 `couples` / `couple_members`。
6. **加入 RPC**：应看到 `POST /rest/v1/rpc/join_couple`，请求参数是 `p_couple_id`。注意查看响应错误：编号不存在、空间已满、已加入其他空间等应由服务器拒绝。核对调用后双方首页显示同一 UUID。
7. **RPC 错误分类**：`401` 通常检查会话是否已确认且有效；`403` 检查 RLS / 函数执行权限；`404` 或 `PGRST202` 检查目标项目是否应用包含两个 RPC 的迁移及参数签名；其他 `4xx` 查看响应中的业务错误。不要通过关闭 RLS、使用 service role key 或在前端写入私钥绕过错误。
8. **退出与会话恢复**：确认 `/auth/v1/logout` 成功，刷新后不再恢复已退出账户。Application / Storage 中可在本机核对 Supabase 会话存储是否更新；不要复制或导出存储里的凭证。

验收记录建议只保留：浏览器环境 A / B、测试日期、步骤结果、脱敏错误和用于本次配对的空间 UUID。测试账户清理应另行按项目的数据管理流程处理，不需要为了运行此流程执行数据库重置。
